# 任务进度与续接

任务状态存于开发项目的 `.scratch/matt-mainflow/<task-slug>/state.md`，每个任务一份。工单路径见 [规格与工单存放](../SKILL.md#规格与工单存放)。状态文件记录链接、决策摘要和证据。

## 状态格式

创建前检查同名任务，使用未占用的简短 slug；不要覆盖旧任务。项目以仓库标识或项目名称记录，产物路径相对项目根目录，避免依赖某台机器的目录布局。写入前重新读取文件，保留已有记录及他人更新；存在冲突时先核对，不用旧副本覆盖新状态。

```markdown
# <任务名称>

- 项目：<仓库标识或项目名称>
- 目标：<一句话目标>
- 路线：<选择的阶段、跳过依据及授权范围>
- 当前阶段：<1–6 或初始化>
- 状态：<进行中 / 待确认 / 暂停 / 阻塞 / 已完成>
- 下一步：<具体动作；等待哪项决定>
- 恢复位置：<正在处理的工单、未完成动作；无则省略>
- 当前实现批次：<批次标识、选定工单及边界；未到实现阶段填无>
- 更新时间：<实际本地时间及偏移>

- 分支和起始 HEAD：
- 无起始提交时的文件清单及内容快照引用：
- 起始已有改动：
- 本任务工单及状态：
- 本任务文件、提交和差异范围：
- 已确认的规格或行为与验收：<规格相对路径及版本，或直接记录已确认的行为、适用范围和验收条件>

## 验证

- <检查内容、实际命令或操作、结果、对应代码版本或差异、证据位置>
- 未验证：<缺失验收及原因>

## 待确认动作

- 动作标识：<本任务内唯一编号；没有待确认动作填无>
- 任务及目标阶段：
- 具体动作及范围：<例如确认当前规格并进入拆工单>
- 绑定版本：<产物相对路径，以及内容摘要哈希或不可变修订号；仅用路径、时间或可变分支名不足以识别版本>
- 确认状态：<待确认 / 已确认 / 已失效 / 已执行>
- 用户确认依据：<本次实际回复及其上下文摘要；未确认填无>

- <实际时间>：<用户决定、阶段转换或范围变化，简短记录依据>
```

阶段状态可用：未开始、进行中、待确认、已确认、已完成、已跳过、需复核。记录每个已跳过阶段的依据及路线授权，例如一次可完成的单行为任务用这里的验收记录代替规格和工单。已有记录缺少路线或规格字段时，沿用已确认的范围，按已读产物和实际决定补记。尚未执行的测试填未验证。按选定路线的实际产物和验证证据判断任务是否完成。

阶段产物完成、用户确认、暂停、失败阻塞及范围变化时更新状态。普通工具调用不逐条记流水账。用户确认只记录本次确实出现的决定，不补造历史确认或时间。

## 确认与续接

已建档的任务在展示待确认动作时记录其编号及绑定版本。首次启动的确认保留在当前对话，获准开始时将实际答复和范围写入新状态。

暂停后或换会话首次收到「继续」时，核对记录并展示恢复点。已授权的动作从未完成处接着做。待授权的动作重新展示其编号、具体范围和绑定版本，收到针对此动作的答复后才执行。一次确认可覆盖明确列出的连续动作。收到针对当前卡片的确认后，核对任务、目标阶段、动作范围及绑定版本。一致且获得实际答复才标记已确认，执行完毕后标记已执行。再次收到确认时从当前进度判断下一步，已执行的动作不重复发布或执行。发现变化时标记已失效，展示差异和新动作等待确认。恢复已确认的动作时先核对已落盘的结果，再从尚未完成的部分接续。暂停保留待确认动作，恢复时仍要核对版本。旧记录缺少确认字段时依据实际产物补记，授权以用户实际回复为准。清理动作按「收尾整理与清理」单独确认。

需要确认的拆分草案保存于该任务的状态记录或其引用文件。绑定展示过的草案正文及其来源规格版本。草案在状态文件内时，用草案段落本身计算摘要。确认前正式工单目录无新增工单。

## 审查输入及证据

每次代码审查前读[审查输入及证据](implementation.md#审查输入及证据)。

## 收尾整理与清理

选定路线的验收和审查完成后，确认复盘已完成或按路线跳过。按用户的收尾授权标记开发任务已完成并报告验证结果，再按下列步骤归档。普通确认、「继续」和「收尾」只推进各自授权的动作。删除依第 3 步单独授权。

1. **盘点与归并。** 根据状态、工单和产物记录盘点本任务在 `.scratch/` 下的全部文件，核对文档、代码和其他任务是否引用。将仍有价值的内容整理后并入现有正式位置，例如规格、决策及必要的脱敏验收证据归入对应的 `docs/` 文档，可复用的实现或测试并入相应源码或测试目录。内容已被正式成果覆盖时沿用该成果。更新受影响的正式引用，检查测试与文档链接。若归属不明或其他任务仍依赖旧路径，先解决归属或引用再开放清理。
2. **提交与清单。** 正式成果和引用更新随任务提交，按已有授权执行 Git 提交。需要提交但尚未获授权时，报告待提交内容，保留临时原件并等待。确认正式位置及对应提交后，在当前任务状态记录项目、任务、提交及完整清理清单（项目相对路径与文件摘要），并向用户展示清单和正式去向。当前状态文件也列入清单，以该待确认记录作为它自身的版本依据。
3. **确认与删除。** 用户看过清单并回复「清理本任务」后，复核正式成果、引用、文件归属和版本。发现变化时重新展示清单，等待确认。只删除确认过且归属于当前任务的 `.scratch/` 文件，确认路径边界，遇到符号链接仅处理链接本身。最后删当前任务的状态文件及因此变空的任务子目录。核对本任务临时产物已全部清理，报告正式成果、提交与结果。再次收到清理指令但没有待确认记录时，报告当前状态，无需执行删除。

## 回退与变更

- 需求变化：规格、工单、实现、审查、复盘逐项判断影响，受影响项标“需复核”。
- 规格变化：从工单向后判断影响；与变化无关的已有工作保留有效。
- 工单或其验收证据失效：核对受影响的工单、实现和审查。前置工单需复核时，依赖它的未完成工单恢复阻塞，已完成的下游工单按影响标记需复核。
- 代码变化：对应测试和审查结果需核对是否仍适用。
- 返回某阶段仅表示重新进入该阶段；保留已有产物和代码。

续接时检查实际项目、分支和产物是否仍匹配。记录丢失时根据现有产物提出恢复方案，获得用户确认后重建；不假装记得不存在的阶段决定。目录中不存凭据、私人会话原文或无关资料。
